# قرارداد بک‌اند — تأیید حضور و پیگیری منشی

## هدف و تغییر دامنه

این سند قرارداد موردنیاز فرانت جدید داشبورد منشی را مشخص می‌کند:

1. قابلیت و endpoint مستقل «تخصیص دکتر» به‌طور کامل حذف می‌شود؛
2. نام دکتر فقط هنگام بررسی حضور بیمار و به‌صورت دستی توسط منشی ثبت می‌شود؛
3. بخش قدیمی «دفترچه یادداشت/دفترچه پیگیری» وجود ندارد و بخش عملیاتی آن با نام «پیگیری» جایگزین شده است؛
4. نتیجه پیگیری ثبت‌شده توسط منشی در بخش «پیگیری‌های منشی» داشبورد مشاور نمایش داده می‌شود.

این تغییر نباید قابلیت پیگیری را حذف کند. فقط مفهوم دفترچه یادداشت مستقل حذف شده و نتیجه پیگیری، یک رکورد ساختاریافته و قابل مشاهده برای مشاور است.

## ۱. حذف کامل تخصیص مستقل دکتر

endpoint زیر باید حذف یا غیرفعال شود و هیچ Permission، منو یا گردش‌کار مستقلی برای آن باقی نماند:

```http
POST /Reservation/{reservationId}/assign-doctor
```

اگر حذف فوری endpoint به‌دلیل سازگاری نسخه‌ای ممکن نیست، تا پایان دوره مهاجرت پاسخ `410 Gone` برگردد. هیچ کلاینت جدیدی نباید از این مسیر استفاده کند.

## ۲. بررسی حضور و ورود دستی دکتر

### درخواست

```http
POST /Reservation/ReviewAttendance
Authorization: Bearer <secretary-token>
Content-Type: application/json
```

```json
{
  "reservationId": 1245,
  "patientReceivedService": true,
  "doctorName": "دکتر سعید مقدم",
  "note": "خدمت طبق برنامه انجام شد"
}
```

| فیلد | نوع | اجباری | قاعده |
|---|---|---:|---|
| `reservationId` | `long` | بله | رزرو موجود و قابل مدیریت توسط منشی |
| `patientReceivedService` | `bool` | بله | نتیجه نهایی بررسی منشی |
| `doctorName` | `string` | بله | پس از Trim بین ۲ تا ۱۲۰ نویسه |
| `note` | `string?` | خیر | پس از Trim حداکثر طول مطابق OpenAPI |

### قواعد تراکنش

- نام دکتر از JWT، رزرو قبلی یا assignment استنتاج نشود؛ مقدار همین درخواست منبع نهایی است.
- `doctorName` همراه نتیجه بررسی حضور، در یک تراکنش ذخیره شود؛ ثبت یکی بدون دیگری مجاز نیست.
- بک‌اند مقدار را Trim کند و مقدار خالی/Whitespace را با `400 Bad Request` رد کند.
- فقط منشی دارای Permission تأیید حضور و دسترسی به رزرو مجاز به عملیات است؛ در غیر این صورت `403 Forbidden` برگردد.
- رزرو ناموجود `404` و رزرو قبلاً نهایی‌شده `409 Conflict` برگرداند.
- retry همان درخواست باید idempotent باشد و امتیاز یا رویداد تکراری ایجاد نکند.
- Audit شامل `secretaryUserId`، زمان، نتیجه، نام دکتر و مقدار قبلی/جدید باشد.

### پاسخ موفق

```json
{
  "isSuccess": true,
  "message": "بررسی حضور بیمار ثبت شد",
  "data": {
    "reservationId": 1245,
    "patientReceivedService": true,
    "doctorName": "دکتر سعید مقدم",
    "secretaryReviewedAt": "2026-08-25T10:30:00Z"
  }
}
```

فهرست رزروها می‌تواند `doctorName` نهایی را برای نمایش تاریخچه برگرداند، اما فرانت هنگام بررسی جدید آن را پیش‌فرض فرم قرار نمی‌دهد و منشی باید نام را دستی وارد کند.

## ۳. ثبت پیگیری منشی

بخش «پیگیری» باید رکورد ساختاریافته ایجاد کند و حداقل شامل بیمار/رزرو، وضعیت تماس و نتیجه پیگیری باشد. قرارداد فعلی فرانت:

```http
POST /secretary/follow-ups
Authorization: Bearer <secretary-token>
Content-Type: application/json
```

```json
{
  "patientId": 876,
  "contacted": true,
  "contactResult": "بیمار پاسخ داد و زمان مراجعه را تأیید کرد"
}
```

- `contactResult` نتیجه پیگیری است، نه یادداشت خصوصی منشی؛ پس باید برای مشاور همان بیمار قابل مشاهده باشد.
- نتیجه پس از Trim اجباری و حداکثر ۲۰۰۰ نویسه باشد.
- رزرو و مشاور از سمت کلاینت انتخاب نمی‌شوند؛ بک‌اند هر دو را از بیمار و assignment معتبر او resolve می‌کند.
- منشی فقط پیگیری‌های مجاز خود را ایجاد/ویرایش کند و تمام تغییرات Audit شوند.
- حذف فیزیکی ممنوع است؛ در صورت پشتیبانی از حذف، soft delete انجام شود و رکورد حذف‌شده به مشاور نمایش داده نشود.

## ۴. نمایش پیگیری منشی در داشبورد مشاور

```http
GET /consultant/follow-ups?page=1&pageSize=20&search=
Authorization: Bearer <consultant-token>
```

بک‌اند باید شناسه مشاور را فقط از JWT استخراج کند. ارسال `consultantProfileId` از query یا body نباید مبنای مجوز قرار گیرد.

```json
{
  "items": [
    {
      "id": 91,
      "patientName": "علی رضایی",
      "phoneNumber": "09120000000",
      "reservationDate": "2026-08-27T00:00:00+03:30",
      "reservationTime": "14:30",
      "secretaryName": "مریم احمدی",
      "contacted": true,
      "contactResult": "بیمار پاسخ داد و زمان مراجعه را تأیید کرد",
      "createdAt": "2026-08-25T10:30:00Z",
      "updatedAt": "2026-08-25T10:30:00Z"
    }
  ],
  "totalCount": 1,
  "page": 1,
  "pageSize": 20
}
```

### الزامات دسترسی و فیلتر

- فقط رکورد بیمارانی برگردد که assignment فعال آن‌ها متعلق به مشاور احرازشده است.
- جستجو روی نام بیمار، تلفن و نتیجه پیگیری انجام شود.
- مرتب‌سازی پیش‌فرض `createdAt DESC` باشد.
- شماره تماس فقط برای مشاور مجاز همان بیمار برگردد.
- رکوردهای soft-deleted، assignmentهای نامرتبط و یادداشت‌های داخلی/خصوصی برگردانده نشوند.
- ویرایش پیگیری باید در دریافت بعدی بلافاصله مقدار جدید `contactResult` را نشان دهد.

## ۵. مهاجرت داده

- داده‌های قدیمی دفترچه که واقعاً نتیجه تماس هستند، به رکورد پیگیری با `contactResult` منتقل شوند.
- یادداشت‌های خصوصی یا عمومی‌نبوده نباید به endpoint مشاور مهاجرت یا افشا شوند.
- ارتباط با بیمار، رزرو و assignment حفظ و رکوردهای بدون مالک برای بررسی دستی گزارش شوند.
- endpointهای عمومی دفترچه یادداشت پس از مهاجرت حذف یا `410 Gone` شوند.

## ۶. معیار پذیرش بک‌اند

- [ ] هیچ endpoint فعال برای تخصیص مستقل دکتر به بیمار توسط منشی وجود ندارد.
- [ ] بررسی حضور بدون `doctorName` معتبر با `400` رد می‌شود.
- [ ] نام دکتر و نتیجه بررسی حضور اتمیک و Audit شده ذخیره می‌شوند.
- [ ] منشی می‌تواند نتیجه پیگیری را ثبت و ویرایش کند.
- [ ] مشاور فقط پیگیری بیماران متعلق به خود را می‌بیند.
- [ ] `contactResult` ثبت‌شده منشی بدون تبدیل به یادداشت خصوصی در داشبورد مشاور برمی‌گردد.
- [ ] pagination، search، مرتب‌سازی و soft delete رعایت می‌شوند.
- [ ] تست دسترسی افقی ثابت می‌کند مشاور نمی‌تواند پیگیری مشاور دیگر را دریافت کند.
